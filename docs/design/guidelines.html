Design guidelines

The reference every screen is checked against. Colours, type, spacing and components on this page are rendered from tokens.css and the mockup CSS, not drawn. The app serves this page at /design for signed-in users, rendered from the install's own two theme values.

1. Principles

Five rules that decide the look when nothing else does.

  1. Calm monochrome surfaces. The neutral scale carries the page: canvas, cards, borders and text. Panels are separated by 1 px lines, not by colour.
  2. One accent, used for selection, focus and small signals, never large fills. A selected item, the focus ring, a state dot, a keyterm highlight. No green buttons, no tinted page backgrounds.
  3. Text carries state; colour only confirms it. Private, Shared, Company, Transcribing, Ready, Waiting for network: every state is a word first.
  4. Behaviour before polish. A screen is done when the rules in behaviour.md hold on the running app. Section 9 lists them.
  5. The product name is the install's. The interface shows the name from settings, for example "Primux Møder". mtxt appears only in About and on GitHub, never on the login page, in the recorder or in the tray.

Motion

State changes use --motion-duration (150 ms) with ease-out for background, colour and border. Hover the buttons below. Layout, list updates, transcript scrolling and audio activity are not animated.

Under prefers-reduced-motion: reduce, tokens.css sets the duration to 0 and removes every transition and animation. Nothing waits for an animation to finish.

8. Writing in the interface

English is the source of every string; Danish is the first translation. The rules below hold in both.

  • Sentence case everywhere: "New meeting", not "New Meeting".
  • No exclamation marks.
  • Buttons are verbs: "Upload audio", "Rename speaker", "Export", "Try again".
  • State words are short and fixed: "Saving", "Saved", "Not saved"; "Transcribing", "Ready"; "Waiting for network".
  • An error says what happened and the next step: "Could not load meetings" with "Try again"; "The server rejected the file · Contact your admin".
  • A thing has one name on every screen: a meeting is a meeting, never a session or a recording.

Translation

Strings live in locale files, one set per app, with flat keys namespaced by screen or component: nav.myMeetings, library.search.placeholder, meeting.tabs.recap, recorder.queue.pendingNetwork. The first two are locales/en.json and locales/da.json.

Never build a sentence from pieces. Counts and names go in as arguments, in ICU message syntax, so each language can order and inflect them:

"library.showing": "Showing {shown} of {total, plural, one {# meeting} other {# meetings}}"
"library.showing": "Viser {shown} af {total, plural, one {# møde} other {# møder}}"

Dates, times, durations and lists go through the locale: "22 Oct 2026" and "22. okt. 2026", "09:00" and "09.00", "42 min" and "42 min.", "Mette, Jonas and Søren" and "Mette, Jonas og Søren".

Names, meeting titles, transcript text, recap content and keyterms are data, not interface. They are never translated, and they carry their own lang attribute.

9. Behaviour rules

The 13 rules from behaviour.md, one line each. The file holds the checks.

  1. 1Autosave, never a Save button as the safety net. The editor says Saving, Saved or Not saved.
  2. 2Small changes show at once and roll back with a reason when the server refuses.
  3. 3Archive is not delete. Delete names its consequence; retention is announced a week ahead.
  4. 4Two people do not overwrite each other. A stale window says Changed elsewhere · Reload.
  5. 5A link keeps the view: filters, search, page and transcript position live in the URL.
  6. 6Lists have an end and a count. Loading, failure, count and end of list are visible states.
  7. 7One way of working across screens. Search, filters, rows and errors are built once.
  8. 8Empty is three different states: first use, no matches, failed fetch.
  9. 9An error says what to do, at the field and with the next step.
  10. 10One thing per screen asks for attention: one primary button.
  11. 11Keyboard and focus. Real controls, a visible ring, dialogs that trap and return focus.
  12. 12Motion is short and optional: 150 ms, none under reduced motion.
  13. 13Real data breaks pretty layouts. Test 4-hour meetings, 14 speakers, 120-character titles.

Definition of done for a screen

  • Which of rules 1 to 13 apply, and the check that was run for each.
  • A screenshot at 1280 px and at 390 px on the real build.
  • A keyboard-only walk through the screen's main task.
  • The three empty states wherever a list is involved.

10. Checklist

A screen is accepted when every line holds.

  • Tokens only: no literal colour in a component; every colour is a variable from tokens.css.
  • Both themes look right, light and dark.
  • Screenshots at 1280 px and at 390 px.
  • A keyboard-only walk through the main task, with a visible focus ring all the way.
  • Usable at 200 percent browser zoom.
  • The three empty states where a list is involved.
  • Every string comes from the locale files, in English and Danish; no string in a component.
  • The behaviour rules that apply are named, and each was checked on the running app.
